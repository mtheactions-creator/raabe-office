# Step 0 report: which editing engine feels like Word?

Date: 2026-10-13 · Measured with `tools/feel-lab` (see `docs/FEEL.md`) · Raw data in
`tools/feel-lab/results/2026-10-13-*.json`

## Question

Two prototype editors were built on Tauri 2 / WebView2 (see `docs/ARCHITECTURE.md`):

- **A, native editing:** the browser's `contenteditable` (via ProseMirror) does input,
  caret, selection and text layout.
- **B, controlled editing:** our own model, line breaking, pagination, caret and
  selection; the browser only renders text and delivers raw keyboard input.

Both were measured against Microsoft Word (M365, 16.0.20430) on the same document, in the
same screen rectangle, at 100 % zoom, with real keyboard and mouse input.

## Results

| Metric | Word | A (native) | B (controlled) |
|---|---|---|---|
| **F1** keystroke → screen, median (end of document) | 36.6 ms | 32.4 ms | **32.2 ms** |
| **F1** keystroke → screen, median (page 12 of 50, reflowing paragraph) | 35.5 ms | 32.0 ms | **32.2 ms** |
| **F1** keystrokes one frame late (> 50 ms) | 2 / 120 | 0 / 120 | 14 / 120 |
| **F3** behaviours identical to Word (50 cases) | reference | 31 / 50 | **50 / 50** ¹ |
| **F4** line breaks identical to Word (50 pages, 2,000 lines) | reference | 2,000 / 2,000 | **2,000 / 2,000** |
| **F4** page breaks identical to Word | reference | none (no pages) | **50 / 50** |
| **F5** start → document text visible, median | 1,185 ms | 549 ms | **526 ms** |

¹ 49/50 in the recorded run. The 50th case ("double-click a word in parentheses")
failed because Word itself did not react in that run; repeated runs give the same
selection in Word and B.

The display runs at 30 Hz, so screen timings are quantised to ~33 ms. All three
editors show a typed character on the next refresh in the normal case; the remaining
differences are smaller than one refresh.

## What we learned

1. **B can match Word exactly.** Its own line breaking reproduces Word's line and page
   breaks character for character, including widow/orphan control and "keep with next".
   Its own selection logic reproduces Word's rules once they are known. The catalogue
   found eight differences in the first B run (smart replace keeps the trailing space,
   smart paste inserts a space, Strg+Entf inside a word keeps the following space, one
   undo step per typing burst, clicks in paragraph spacing go to the line below); each
   took minutes to fix.
2. **A cannot be made to match Word.** Its 19 failing cases are the browser's own
   behaviour: no word snapping while dragging, no sentence selection with Strg+click,
   no selection bar in the left margin, different triple-click, double-click and
   Strg+↑/↓ rules, clicks beside a line land elsewhere. These are hard-wired into
   `contenteditable` and can only be overridden by re-implementing them, which is
   approach B anyway. A also has no pages, and pagination is very hard to add to it.
3. **The "web app" feel has measurable causes, and they can be fixed.** B was initially
   one full frame slower than Word (66 ms). The cause was the caret blink animation:
   restarting a browser animation on every keystroke delayed the frame. A plain timer
   fixed it (32 ms). This is the kind of detail that makes an editor feel "slightly less
   immediate", and the harness found it within minutes.
4. **Start time is less than half of Word's**, with room to improve (WebView2
   initialisation dominates; the editor itself is ready in milliseconds). The whole
   prototype app, both engines included, is a 4.3 MB executable.

## Open issues (to address in Step 2, not blockers)

- B shows ~12 % of keystrokes one frame late (A: 0 %). The JavaScript work per keystroke
  is 0.3-0.6 ms, so the cause is in rendering; to be found with a trace.
- Only a simple document was tested (one font, left aligned, no tables, images or
  formatting). Fidelity has to be re-checked as each feature is added.
- Not yet measured: F2 (frame stability while scrolling/dragging) and F6 (text rendering
  compared with Word).
- B must build what A gets for free: IME details, screen-reader accessibility,
  spell-check underlines, native context menus. All are known, solvable work.
- The harness should run Word's reference twice and flag inconsistent results (see ¹).

## Recommendation

**Use approach B (controlled editing) for RaabeWrite**, and the same architecture for
the text inside RaabeCalc cells and RaabePresent text boxes. It is the only approach
that reached Word's behaviour and pagination, and after one fix it is as fast as Word.
Tauri 2 stays (D-006): nothing in the measurements points to the web stack itself as
the problem.
